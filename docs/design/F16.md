# F16 — Types: think in things, not files (from Capacities)

_The design as agreed before it was built. Done: see [CHANGELOG.md](../CHANGELOG.md); what's still open is in [BACKLOG.md](../BACKLOG.md)._

**The idea.** Capacities organises knowledge by *what a thing is*, not *where it's filed*. Every
note is an **object** with a **type** (Person, Meeting, Book, Project), and each type has its own
properties, template and page. You link things rather than file them: a resource can serve three
projects at once without being moved. Its guide to choosing a structure is worth keeping:

| You want to… | Use |
|---|---|
| say what a note *is* and give it a shape | a **type** with **properties** |
| say what a note is *about*, across types | a **tag** |
| connect one type to another (a Meeting's attendees) | a **relation** property |
| sort within one type (a Book's reading status) | a **select** property |
| gather things by hand | a folder, or a list of links |
| gather things by rule, always up to date | a **saved view** (a query) |

**Commonplace's version stays plain markdown**, so other Markdown editors and every other tool can still read it:

- **A type is a note** in `Types/` (`Types/Person.md`). Its frontmatter lists the properties
  (name, kind: text, number, date, checkbox, list, select with options, or a relation to
  another type), an icon and a colour. Its body is the template for new notes of that type. Types
  live in the vault, so they're shared with members, versioned and exported like any note.
- **An object is a note with `type: Person`** in its frontmatter. Relations are written as
  wikilinks (`attendees: ["[[Sam]]", "[[Alex]]"]`), as the `.base` format expects, so they count as
  links and appear in backlinks.
- **Folders stay**, for compatibility with other Markdown editors and for people who like them, but nothing needs
  them: types, tags, links and saved views do the organising.

All six steps are done (see Done). Still open: turning a line into a typed note with `#Type`
inline, as Capacities does.

**Risks to design for.**
- **Two ways to say the same thing.** A property called `type` may already mean something else
  in someone's imported vault. Keep `type:` as the key, but let a vault choose another name in
  settings before it starts.
- **Schema drift.** Changing a type's properties mustn't rewrite every note. Notes keep whatever
  they have, and the type page shows missing or extra properties so they can be fixed in bulk.
- **Speed.** Type pages query frontmatter. Postgres already stores it as JSON per note
  (`notes.frontmatter`), so an index on `frontmatter->>'type'` keeps a type page instant at
  10,000 notes.

**Done when** I can make a Person type with a role (select) and a company (relation to an
Organisation type), and turn three existing notes into People. Then a Meeting type whose
attendees are People, so that:
- Sam's page shows "Attendee of: 2 meetings";
- the Person type page shows a table I can sort by company and save as a view that opens in
  other Markdown editors;
- yesterday's daily note lists the two meetings I made then;
- the AI can file five inbox notes into the right types after I approve.
