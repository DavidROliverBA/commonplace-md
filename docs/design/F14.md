# F14 — GitHub vaults: open a repo as a vault, edit on a branch, finish with a pull request

_The design as agreed before it was built. Done: see [CHANGELOG.md](../CHANGELOG.md); what's still open is in [BACKLOG.md](../BACKLOG.md)._

**Built 2026-10-12 (v0.0.21).**

**Size** L, in four steps · **Evidence** `src/transfer.ts:51` (`importFiles` already unpacks a
zip into a vault); GitHub's REST API (zipball, Git Data and Pulls endpoints)

When you choose or create a vault, you can pick **"From GitHub"**, choose a repository (and
optionally a folder in it, such as `docs/`), and it's copied in as a vault you edit in
Commonplace. Your edits are a **branch**: a bar at the top always shows it ("On branch
`commonplace/boiler-notes`, from `main`, 3 notes changed"). From that bar you can **review the
changes**, **open a pull request**, or **cancel the branch** and go back to what's on GitHub.
The point is that a repo of markdown (docs, a vault of notes kept in git, AI-XF bundles) can
be edited with the comfort of Commonplace, and nothing reaches `main` without a PR.

**No `git` on the server.** Render's disk is temporary and the Docker image doesn't need git.
Everything goes through GitHub's API, with the token in an `Authorization` header and never in
a clone URL (the usual `https://token@github.com/...` is exactly what not to do):
- **Copy in:** as built, read the tree at the base commit with the Git Trees API and fetch
  each wanted file as a blob (`src/git.ts` `copyIn`), not the zipball first planned: only the
  chosen folder and file types are downloaded, each file's sha is known for later updates, and
  size limits apply before anything is fetched. Record the base commit SHA and each file's
  original content, so changes can be shown and committed.
- **Commit:** create blobs for the changed files, a tree on top of the base tree, a commit
  whose parent is the base, then create or move the branch ref. One sequence of API calls.
- **PR:** create the pull request and link to it from the bar.

**Signing in to GitHub.** Per person, like F13's AI keys: start with a fine-grained personal
access token (contents and pull requests, chosen repos only), stored encrypted with the same
`SECRETS_KEY`, never shown again. A GitHub App ("Install Commonplace on these repos") is nicer
and gives short-lived tokens; switch to it if this gets used by anyone but me.

**What's copied.** Markdown, `.canvas` (F11) and attachments (pictures, PDFs); everything else
in the repo (code, dot-folders such as app settings and `.github/`) stays on GitHub and is left untouched by the
commit, because the new tree is built on the base tree. Limits on size and file count, as for
zip imports, so a large repo can't fill the 1 GB database.

1. **Copy a repo in (M).** "From GitHub" in the vault picker: connect a token, pick a repo,
   branch and optional folder; the vault is created and filled. A `vault_git` table (vault,
   repo, folder, base branch, base SHA, working branch name) and the original content per file.
2. **The branch bar and changes view (M).** The bar is always visible on a GitHub vault, on
   the laptop and the iPhone. "Review changes" lists added, edited, moved and deleted notes,
   and opens a side-by-side or inline diff of each against the original (this also builds the
   "Note history diff view" idea). A change can be reverted file by file.
3. **Open a pull request (M).** A short form: PR title, description, and the commit message,
   filled in from the changed notes' titles; "Open pull request" commits as described above and
   shows the PR link. Later edits on the same branch become further commits on the same PR
   ("Push 2 more changes"). The bar shows the PR's state (open, merged, closed), checked when
   the vault is opened.
4. **Cancel the branch, and start fresh (M).**
   - **Cancel the branch** (with a confirmation that names how many notes will change back):
     every note returns to the original through `overwriteContent`, so open editors update
     live, and each reverted note's edits stay in its history, so nothing is unrecoverable.
     The GitHub branch is deleted if it was pushed and has no open PR.
   - **After a merge, or when `main` moves on:** "Update from `main`" brings in the new commits.
     Notes you haven't changed are updated in place; notes changed on both sides are merged
     line by line (three-way, using the stored original), and real clashes are shown in the
     changes view to pick a side, never written as `<<<<<<<` markers into a note.

**Decided as part of this item** (F19 adds automatic sending and an opt-in to publish straight
to a branch). One working branch per vault at a time, which keeps the bar
simple. Collaborators in the vault share that branch, and the commit lists them as
co-authors. The branch name is made from the first changed note's title and can be renamed
before the PR.

**Done when** I can pick a private repo of markdown from the vault picker and get a vault; edit
three notes and see "3 notes changed" in the bar on the laptop and the iPhone; review a diff
of each; open a PR with one button and see it on GitHub with only those files changed (code and
dot-folders untouched); cancel a branch and see every note go back to what's on GitHub; update
from `main` after merging without losing anything; and the token never appears in a URL, a
log or a response.
